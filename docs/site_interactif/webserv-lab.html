recv() ne te donne pas une requête

TCP est un flux d'octets. Pas de messages, pas de frontières, jamais de « voilà, c'est tout ». Appelle recv() et regarde ce qui arrive vraiment.

0 appel · 0 octet
Buffer vide. On attend le premier recv().

Le code que ça implique

// à chaque recv(), on accumule — on ne parse rien avant d'être sûr buf.append(tmp, n); size_t p = buf.find("\r\n\r\n"); if (p == std::string::npos) return; // en-têtes incomplets → on attend // headers = buf[0, p) · body commence à p + 4 (pas +2 !)

C'est le seul moyen de savoir que les en-têtes sont finis. Sans \r\n\r\n, tu ne peux pas distinguer « requête terminée » de « réseau lent ».

——sockets

05

Un fd n'est pas un octet

Le file descriptor ne traverse pas le réseau. C'est un int local, un index dans ta table. Ce qui traverse, ce sont des octets anonymes. Chaque côté a sa propre poignée.

La socket d'écoute ne transporte aucune donnée. Elle ne fait qu'annoncer des arrivées.

Le piège : les fd se recyclent. Le client sur le fd 5 part, tu fais close(5) — le suivant récupère 5. Si une référence traîne encore, tu écris au mauvais client. close() et nettoyage de tes structures : même instant, toujours.

——cgi

06

Le CGI ne connaît pas HTTP

Le script croit tourner dans un terminal. Il lit stdin, il écrit sur stdout. C'est toi qui traduis la requête en variables d'environnement. Ajoute un header et regarde.

Variable d'envValeur

La règle des HTTP_*

Chaque header devient une variable : majuscules, tirets remplacés par des underscores, préfixe HTTP_. User-Agent → HTTP_USER_AGENT. Le sujet l'exige : « The full request must be available to the CGI ». Oublie ça, et le script ne voit ni les cookies ni rien.

Le plan de câblage

// PARENT — tout est construit AVANT le fork pipe(in); pipe(out); pid = fork(); if (pid == 0) { // ENFANT : rien que des syscalls dup2(in[0], STDIN_FILENO); // 0 → le pipe. Comme minishell. dup2(out[1], STDOUT_FILENO); // 1 → le pipe // fermer TOUS les autres fd (sockets, epoll...) sinon le port reste pris chdir(dir); // chemins relatifs du script execve("/usr/bin/python3", argv, envp); // chemin ABSOLU, pas de PATH _exit(1); } // PARENT : les 2 pipes entrent dans poll(), comme n'importe quelle socket. // Jamais de write() bloquant : le buffer pipe fait ~64 Ko → deadlock garanti.

Ce que le CGI renvoie

Content-Type: text/html <html>...

Pas de HTTP/1.1 200 OK ! La status line, c'est toi qui la fabriques. Si le script envoie Status: 404, tu utilises ce code. S'il envoie Location:, tu rediriges. Sinon, 200.

Deux pièges du sujet

Chunked. Le CGI n'y comprend rien. C'est ton serveur qui dé-chunke, reconstitue le body, et fixe CONTENT_LENGTH à la vraie taille. Le script lit jusqu'à EOF — c'est-à-dire jusqu'à ce que tu fermes ton bout du pipe.

Timeout. waitpid avec WNOHANG, toujours. Un script en while(1) doit être tué et donner un 504. Sinon « a request should never hang indefinitely » saute.

CGI ? on fork. → on prépare la réponse (du TEXTE) dans out[5] poll() dit : fd 5 est inscriptible → send() ce qu'on peut, on garde le reste → tout envoyé ? keep-alive : on recommence. → sinon close(5) + on efface buf[5] et out[5]

Tout webserv tient là-dedans. Le CGI n'ajoute rien de neuf : deux pipes de plus dans le même poll(), avec les mêmes règles.
